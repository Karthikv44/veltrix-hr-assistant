# ADR 0001: Vector Store Architecture & Hybrid Retrieval

## Status
Accepted

## Context
TASK.pdf requires an embedded vector store running locally without external services (e.g., Chroma, FAISS, Qdrant).
The system must support hybrid retrieval (dense semantic search + BM25 lexical search) with strict access control pre-filtering (role access level, region, effective date).
No document the requester is not allowed to read may ever be scored or sent to the LLM.

## ChromaDB Investigation & Capabilities
An evaluation of current ChromaDB features shows:
1. **Metadata Filtering**:
   - Chroma supports scalar metadata filtering using `$eq`, `$ne`, `$gt`, `$gte`, `$lt`, `$lte`, `$in`, `$nin`.
   - Complex boolean logic is supported using `$and` and `$or` arrays.
   - Crucially, Chroma **does not support list-valued metadata fields** in `where` queries.
   - Therefore, list-valued document attributes such as `regions: ["IN", "US"]` or `["GLOBAL"]` must be flattened at ingestion into boolean scalar flags: `region_IN: True`, `region_US: True`, `region_DE: True`, `region_GLOBAL: True`.
   - Dates are converted to comparable integer scalars: `effective_int: YYYYMMDD`.
   - Access levels are mapped to ordinal integers: `access_rank: all=0, managers=1, hr=2`.

2. **Native Sparse / BM25 Search**:
   - Chroma has introduced experimental schema/sparse indexing APIs (e.g. `SparseVectorIndexConfig`, `ChromaBm25EmbeddingFunction`), but this functionality is **only operational in Chroma Cloud** or distributed server setups.
   - In open-source, embedded single-node deployments (`chromadb.PersistentClient`), native sparse index creation raises `Schema reconciliation failed: Sparse vector indexing is not enabled in local`.

## Decision
1. **ChromaDB Adapter**:
   - Use `chromadb.PersistentClient` in cosine distance space (`"hnsw:space": "cosine"`).
   - Set `anonymized_telemetry=False`.
   - Always supply precomputed embeddings generated by `fastembed` (BGE small model). Never use Chroma's default download-at-runtime embedding function.
   - Execute dense retrieval with strict Chroma `where` filters constructed from `RetrievalScope`.

2. **In-Process BM25 Lexical Retrieval**:
   - Implement lexical search using an in-process BM25 engine (`rank_bm25`).
   - BM25 candidate scoring is restricted strictly to the eligible chunk IDs determined by `RetrievalScope` (derived from the SQLite chunk index).
   - Ineligible chunks are never scored or retrieved.

3. **Reciprocal Rank Fusion (RRF)**:
   - Combine top dense candidates and top lexical candidates using Reciprocal Rank Fusion ($k=60$).
   - Group chunks by `doc_id` (limiting to the top 2 chunks per document) to ensure competing policy versions are both represented for the deterministic precedence resolver.
   - Deterministic tie-breaking on `(score, chunk_id)`.

## Consequences
- Clean separation between storage adapter (`VectorStore` interface) and retrieval orchestration.
- Absolute security compliance: ineligible documents are filtered out before scoring in both dense and lexical channels.
- Fully offline capable within Docker, with zero network dependencies at runtime.
